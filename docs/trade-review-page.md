# 복기 페이지(`/reviews`) 구상

`docs/trade-review-direction.md`의 Phase 1(최소 복기 MVP)을 기준으로, Phase 2·3을 같은 화면에 이어 붙일 수 있게 잡은 화면 구상이다.

## 1. 왜 `/stats` 탭이 아니라 별도 페이지인가

- `/stats`는 "숫자를 보는" 화면이고, 복기는 "입력하고 결론을 남기는" 작업 흐름이다.
- 복기 대기 거래 처리(입력)가 화면 맨 위에 와야 하는데, 통계 페이지에 넣으면 기존 차트·그룹표가 밀려난다.
- 메뉴: `StockNav`에 `통계` 다음 `복기` 추가, 모바일 `BottomTabBar` 더보기에 추가. 복기 대기 건수를 배지로 표시.

## 2. 화면 구성 (위 → 아래)

### ① 기간·계좌 필터

`이번 주 | 이번 달 | 지난달 | 직접` + 계좌 선택. 기준일은 **최종 매도일**(현재 `/stats`와 같은 기준).

### ② 복기 대기 (핵심 습관 루프)

- 대상: 최종 매도 완료(`isCompleted`) + `reviewedAt` 없음. 기간 필터와 무관하게 **전체 미복기 건**을 보여준다.
- 카드 한 장에서 끝나는 빠른 복기 — 목표 10초:
  - 자동 평가 배지(아래 3장) — 사용자는 읽기만
  - 청산 이유 칩 1개 선택 (목표가 도달 / 손절 / 추세 이탈 / 기간 만료 / 공포 / 욕심 / 조기 매도 / 종목 이동 / 현금 필요 / 실수)
  - 복기 한 줄 (`exitComment` 재사용)
  - 진입 이유가 비어 있으면 그 자리에서 칩으로 보완
  - `저장` → `reviewedAt` 기록 후 카드 사라짐 / `나중에` → 그대로 둠
- 잘한 점·아쉬운 점 등 상세 항목은 "더 쓰기"로 접어 둔다 (Phase 3, `TradeReview`).

### ③ 기간 요약 타일

총 거래 수 · 순손익 · 승률 · 평균 이익/손실 · 손익비 · 기대값 · **계획 준수율**.
계획 준수율은 "계획이 있는 거래" 중 이탈 없는 비율이며, 계획 없는 거래 수는 따로 표시.

### ④ 결과 × 과정 2×2 매트릭스 (이 페이지의 대표 화면)

|            | 계획 준수 | 계획 이탈 |
|------------|-----------|-----------|
| **수익**   | 좋은 매매 | 운 좋은 매매 |
| **손실**   | 좋은 손실(손절 준수) | 나쁜 매매 |

- 칸마다 건수·합계 손익·평균 수익률. 칸을 누르면 아래에 해당 거래 목록.
- "수익이 났지만 과정이 나빴던 거래는?"(완료 기준 질문)에 바로 답하는 칸이 `운 좋은 매매`.

### ⑤ 계획 지킨 거래 vs 어긴 거래

- 준수/이탈 그룹 평균 수익률·평균 손익 막대 비교
- 손실 거래만: 손절 준수 평균 손실 vs **손절 늦음** 평균 손실 → "손절을 미룬 거래의 손실은 얼마나 커지는가?"
- 이탈 유형별 건수: 보유 초과 / 손절 늦음 / 조기 익절 (`lib/strategy.ts`의 `Deviation` 명칭과 통일)

### ⑥ 이유별 성과 (Phase 2)

탭: `진입 이유 | 청산 이유 | 전략`. 열: 건수 · 승률 · 평균 수익률 · 손익비 · 합계.
표본 3건 미만은 회색 처리. 전략은 기존 `Strategy` 연결(`strategyId`)을 그대로 사용.

### ⑦ 자동 인사이트 문장 (Phase 2)

규칙 기반 2~3줄. 예: "돌파 매매 승률 70%지만 손익비 0.6", "계획 보유기간 초과 거래 평균 -2.1%(준수 거래 +3.4%)".
표본이 적으면 문장을 만들지 않는다.

### ⑧ 기간 복기 노트 (Phase 3)

- 상단에 **지난 기간에 정한 규칙**을 먼저 보여주고 지켰는지 체크
- 작성: 잘한 점 / 가장 아쉬운 매매(거래 선택) / 반복된 실수 / 다음 기간 규칙 1~3개 / 하지 않을 행동
- 저장 시 복기 완료 처리, 기간별 완료 이력 표시

## 3. 거래별 자동 평가 규칙 (`lib/review.ts`, Vitest 테스트 동반)

거래의 `targetPrice`·`stopLossPrice`·`plannedHoldingPeriod`를 기준으로 한다. (전략 페이지는 전략의 % 규칙 기준이라 기준이 다름 — 화면에 "거래 계획 기준"이라고 명시.)

| 항목 | 규칙 |
|---|---|
| 목표가 도달 | 매도 체결 중 하나라도 `price >= targetPrice` |
| 최종 목표 달성 | 가중평균 매도가 `>= targetPrice` |
| 손절가 도달 | 매도 체결 중 하나라도 `price <= stopLossPrice` |
| 손절 늦음 | 손실 거래이고 가중평균 매도가가 `stopLossPrice`보다 허용폭(기본 1%p) 이상 낮음 |
| 보유 초과 | 기존 `planExceeded` |
| 조기 익절 | 수익 거래이고 목표가 미도달 + 청산 이유가 `조기 매도`/`공포` |
| 계획 준수 | 위 이탈(보유 초과·손절 늦음·조기 익절)이 하나도 없음 |
| 계획 없음 | 목표가·손절가·계획 보유기간이 모두 없음 → 준수율 분모에서 제외 |

부분매도 거래는 "목표가 도달"과 "최종 목표 달성"을 분리해 배지 2개로 보여준다.

## 4. 데이터 변경 (Phase 1 최소)

```prisma
model Trade {
  // ...기존
  entryReason String?   // 진입 이유 1개 (추세/돌파/눌림목/실적/수급/뉴스/테마/저평가/배당/충동매매/물타기)
  exitReason  String?   // 청산 이유 1개
  reviewedAt  String?   // 매도 후 복기 완료 시각
}
```

- 복기 한 줄은 기존 `exitComment` 재사용, `tradeScore`는 그대로 두고 참고 표시만.
- `PATCH /api/trades/[id]`에 세 필드 허용. 페이지는 `/stats`처럼 `GET /api/trades` 전체를 받아 클라이언트에서 계산.
- 진입 쪽: `TradeModal`에 진입 이유 칩 한 줄(선택, 비워도 저장 가능). 카톡 파싱 저장 흐름은 변경 없음.
- Phase 3에서 `PeriodReview`(기간 노트), 필요 시 `TradeReview`(상세 복기) 테이블 추가.

## 5. 구현 순서 제안

1. `lib/review.ts` + 테스트 (평가 규칙, 매트릭스 분류, 요약 지표)
2. 스키마 3필드 + PATCH 허용 + `TradeModal` 진입 이유 칩
3. `/reviews` 페이지: ① 필터, ② 복기 대기, ③ 요약, ④ 매트릭스, ⑤ 준수/이탈 비교 + 메뉴 추가
4. (Phase 2) ⑥ 이유별 성과, ⑦ 인사이트
5. (Phase 3) ⑧ 기간 복기 노트 + `PeriodReview`

## 6. 결정 사항 (Phase 1 구현 시)

- 손절 늦음 허용폭: 매수가 대비 1%p 고정 (`STOP_LOSS_TOLERANCE_PCT`)
- 청산 이유를 "목표가 도달"로 골랐는데 실제 매도 체결이 목표가 미만이면: 경고만 표시, 저장은 막지 않음
- 복기 대기: 기본은 최근 30일 매도분, "전체 보기"로 과거 미복기 거래까지 표시
- 거래 수정 창에서 매도 완료 거래에 청산 이유를 남기면 복기 완료(`reviewedAt`)로 처리
- 메뉴 배지(복기 대기 건수)는 모든 페이지에서 거래 전체를 불러와야 해서 보류
